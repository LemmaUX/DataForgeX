# DataForgeX — Project Status

## Project Definition

**DataForgeX** is an Intelligent Infrastructure Observability & Optimization Platform designed to correlate cloud cost, infrastructure performance, application telemetry, and operational change events through a deterministic, evidence-grounded data platform.

The system is designed around a strict separation between:

1. Validated operational data
2. Deterministic analytics
3. Machine learning outputs
4. Evidence retrieval
5. Generative AI
6. Human-approved remediation

Generative AI is not considered a source of truth. Operational claims must be grounded in validated and lineage-tracked evidence.

## Current Status

**Phase:** Requirements Definition / Architecture Gate

**Implementation Status:** Not started

**Architecture Status:** Pending alternatives analysis

**Technology Selection:** Intentionally deferred

The project was intentionally stopped before implementation in order to preserve the requirements-first engineering process.

## Defined Scope

The platform is intended to support:

* Cloud billing ingestion
* Infrastructure metrics ingestion
* Application telemetry
* Operational change events
* Data validation and normalization
* Data lineage
* Deterministic cost/performance analytics
* Anomaly detection and forecasting
* Evidence-grounded LLM investigation
* Human-in-the-loop optimization approval
* Optional controlled remediation
* Replay and historical backfill

## Core Engineering Principles

### Evidence Before Intelligence

AI components operate exclusively over validated and lineage-tracked data.

### Deterministic Source of Truth

Financial, infrastructure, and performance facts are produced by deterministic data pipelines and analytical systems rather than generated by an LLM.

### Explicit Failure Handling

The architecture must account for duplicate events, malformed data, late data, replay, backpressure, dependency failures, and partial system failure.

### Human-Controlled Remediation

Production infrastructure changes require explicit human approval.

### Modular Architecture

Data Engineering, ML, GenAI, Agent, and cloud-specific capabilities are intended to communicate through explicit contracts rather than tightly coupled implementations.

The model is expected to be refined during architecture and data-model review.

## Initial System Contracts

The initial contracts define:

* At-least-once ingestion
* Idempotent processing
* Schema validation
* Data quarantine for invalid records
* Lineage tracking
* Deterministic analytics
* Evidence references for generated answers
* RBAC-based access control
* Explicit human approval for remediation

## Non-Functional Targets

Initial platform targets include:

* Dashboard query latency: <2s p95
* LLM response latency: <10s p95
* Metrics ingestion: 50K metrics/sec
* Metrics freshness: <60s
* Billing freshness: <4h
* Ingestion loss: <0.1%
* Cost attribution error: <1%
* ML false-positive rate: <5%

These targets require workload definitions and benchmark methodology before being considered production SLOs.

## Hackathon Scope

The intended 24–72 hour demonstration focuses on a deliberately constrained vertical slice:

```text
Synthetic Billing + Metrics
        ↓
Normalization
        ↓
Correlation
        ↓
Dashboard
        ↓
Evidence Contract
        ↓
Mock LLM
```

The mock AI layer is intended to consume the same evidence contract that a production LLM implementation would eventually consume.

## Known Open Questions

The following items remain intentionally unresolved before architecture selection:

* Exact storage architecture
* Streaming versus batch boundaries
* Canonical metric representation
* Deduplication scope and idempotency semantics
* Evidence representation and citation validation
* Cost attribution methodology
* Authentication implementation for the MVP
* Dashboard query workload definitions
* ML evaluation methodology
* Module deployment boundaries
* Failure recovery guarantees
* Cloud-specific versus cloud-agnostic capabilities

## Architecture Gate

The project should not proceed directly to implementation.

The next engineering phase is:

**Architecture Alternatives Analysis**

At least three materially different architectural patterns should be evaluated against the requirements, workload, reliability targets, data semantics, operational complexity, and hackathon constraints.

The selected architecture should be justified through explicit trade-offs rather than technology preference.

## Project Principle

> Build the deterministic data foundation first. Add intelligence only where its inputs, outputs, evidence, and failure modes can be verified.
